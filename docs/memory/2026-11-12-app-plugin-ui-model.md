# 2026-11-12 App／插件界面模型：自渲染像素 + 稀疏界面 schema（用户提出，讨论中）

## 用户提出

- 素材预览本质上是一个**功能性插件**：不预览也不影响编辑。所以它的画面应当由原生渲染产出，而不是由 GUI 解码。
- 界面使用 NanoUI 的 API；更本质地说，应当使用**以 NanoUI 为基础、由 Cutrans 自己定义的原生 GUI schema 的 API**。
- **所有 App 和插件**都分成两部分：
  1. 声明并**自渲染的像素**；
  2. **稀疏的界面 schema** 声明。

## 前身

- 2026-10 的 CUI（“可持久化视图声明文档”），以及“统一 UI 规范 = 声明 schema + 装载校验 + 通用解释器 + 属性/命令注册表 + 状态绑定 + 画笔主题 + 外部帧调度”（[17-discussion-history-05](17-discussion-history-05.md)、[17-discussion-history-06](17-discussion-history-06.md)）。
- CUI 在 2026-11-08 统一到 NanoUI 时，随旧 ImGui 栈一起移除（[统一 NanoUI](2026-11-08-nanoui-unification.md)），没有留下继任者。本模型就是那个继任者。

## Claude 的分析（待用户裁定）

- **行业先例**：创作软件的插件普遍采用这种结构。VST3／CLAP 声明参数、由宿主画通用界面，可选自绘编辑器；OpenFX 声明参数描述，叠层交互另走自绘；AE 的特效声明参数后由宿主生成 Effect Controls，可选自定义 UI；Blender 用 RNA 属性加 Panel 注册，视口区域再挂自绘回调。
- **与宪法同构**：界面 schema 是声明，NanoUI 的绘制只是投影；宿主提供机制（怎么画），插件提供策略和内容（画什么）。
- **一份声明，三方投影**：同一份参数 schema 同时生成 GUI 控件、AI 的工具调用 schema（MCP 的 `inputSchema`）和文档。D 声明注册表、`.cut` 节点参数、界面、agent 共用这一个真源，彼此不会漂移。
- **三个层级**：
  1. **标准 schema 控件**：数值、枚举、开关、文本、按钮（命令）、列表、分组、状态。由宿主统一绘制，主题和审美一致，AI 也能读懂。
  2. **宿主提供的富组件**：时间线、曲线编辑器、节点图、色彩选择等。它们以 schema 中的组件类型出现，由宿主用 NanoUI 实现一次，供所有插件复用，避免每个插件各造一遍。
  3. **自渲染像素区**：媒体和独特内容，例如素材预览、波形、示波器、三维视口。由插件的原生渲染器产出，经帧契约交给宿主合成显示。
- **“稀疏”的含义**：schema 只声明语义（参数的类型、范围、单位、分组、命令、状态绑定路径），加上很少的排版提示（顺序、分组、优先级）。具体长什么样由宿主决定。schema 不能演变成一门完整的排版语言，否则会重走 HTML／CUI 的路。表达不了的部分，交给第 3 层自渲染区。
- **交互**：
  - 控件的改动一律走 VM 命令（受管、可撤销），所以每个界面动作天然就是一次工具调用。
  - 自渲染区的指针和键盘输入，以语义事件的形式路由给插件，类似 OpenFX 的 overlay interact。
  - 滚动、焦点、选中这类本地交互状态留在 Shell。
- **对称性**：环境层只认识少数通用动词、与业务无关；GUI 宿主同样只负责解释 schema 和合成像素、与业务无关。

## 对已有问题的影响

- [界面与媒体分家](2026-11-12-gui-media-split.md)中的灰区，在本模型下方向明确：素材预览插件自己负责解码并产出像素，GUI 不再解码。尚未实施。

## 待定

- schema 的最小词汇表，以及它与 D 声明注册表、v4 内存模型的关系：建议用同一套结构体定义。
- 自渲染像素的执行位置：当前为同进程的可信原生代码；不可信插件按 M7 走 WASM 或进程隔离。
- 帧契约的格式：BGRA 缓冲，或 D3D11 共享纹理。
- 首批内置组件的范围。
- 核心 App（桌面框架、停靠、导航）是否也要 schema 化：建议宿主框架直接用 NanoUI 编写，插件贡献的面板走 schema。

## 在本模型下重新评估 NanoUI 的缺口（Claude 分析，2026-11-12 同日）

- **定位变了**：插件和 AI 写的是稀疏 schema，不直接写 NanoUI。NanoUI 成为**宿主内部的实现工具**，只用来实现数量有限的标准控件和富组件。因此“NanoUI 写起来像不像前端”只影响这一组有限的宿主组件，不再影响所有 App 的作者。
- **小众库的锁定风险被隔离**：schema 定义在 `vne`（共享词汇）中，不依赖 NanoUI。即使将来更换 UI 库，也只需重写宿主组件，插件不受影响。
- **重新归类**：
  - 混合模式、滤镜、遮罩、自定义着色器：归媒体渲染一侧，与 GUI 无关，见 [界面与媒体分家](2026-11-12-gui-media-split.md)。
  - 画布缺少贝塞尔／圆弧路径和图形级命中检测、缺少可编辑语法高亮：成为**第 2 层富组件**的实现依赖。节点图、曲线编辑器依赖前者，`.cut` 编辑与审阅组件依赖后者。优先级由首批要做哪些富组件决定。
  - 缺少 `flex-wrap`、grid、`text-align`、百分比尺寸：被宿主的 schema 布局吸收。schema 是稀疏的，宿主只需要少数几种布局模式：表单行、分组、工具条、列表、缩略图网格。其中缩略图网格（资源库要用）需要换行或网格，表单数值右对齐需要 `text-align`；百分比尺寸的需求下降。
  - 项目尚未用上的 kit、`ui.div` 链式写法、motion 与设计令牌：成为第 1 层标准控件的现成实现。kit 已覆盖大部分第 1 层词汇（按钮变体、单选、下拉、数字输入、开关、滑块、标签页、菜单、对话框、toast、tooltip），第 1 层基本就是“schema 类型到 kit 控件”的映射，成本低。
  - 没有热重载、没有检查器：影响下降。schema 是运行时数据，插件界面的改动可以不重新编译 Zig，用 Tester 或离屏预览即可查看；只有修改宿主组件本身时才需要重编译。
- **审美集中化**：审美质量集中在宿主组件与设计令牌这一次性工作上，可以通过离屏预览集中审阅。是否允许离屏预览，仍需用户决定。
- **上游 PR 优先级随之调整**：画布路径 API 最高（第 2 层的依赖）；`flex-wrap` 与 `text-align` 其次（缩略图网格、表单）；百分比尺寸降低；README 的 IME 勘误最轻。
- **现有页面**：桌面、编辑器、资源库、本机文件、CLI、任务页属于宿主一方的首方界面，目前直接用 NanoUI 编写，不必急于 schema 化。迁到 kit 与令牌可以随改随做。

## 问题化归：两类“舒服”（用户提出，2026-11-12 同日）

- 用户把问题化归为两点：
  1. 用 NanoUI 开发、定义 schema 时要舒服，参考**前端开发二级 API 的工作流**；
  2. schema 要定义得让用户用着舒服，参考 **AE 和 Blender 的定义风格**。
- Claude 细化为三方：
  - 宿主开发者：参照前端的设计系统、组件库和 Storybook 式组件画廊；
  - schema 作者（插件开发者与 AI）：参照 Blender 的 `FloatProperty`（min／max、soft_min／soft_max、subtype、unit）与 `layout.prop`，以及 AE SDK 的参数定义（合法范围与滑块范围、参数默认可动画、顺序即界面顺序、topic 分组、稳定的磁盘 id）；
  - 最终用户（创作者）：AE 和 Blender 的操作习惯，由宿主实现一次，所有插件自动获得。包括：在标签上拖动调值、双击输入、恢复默认、关键帧开关、一次拖动算一个撤销步、单位显示、悬停说明（同时作为 AI 的工具描述）、复制粘贴参数、参数搜索。
- **宿主一侧的分层**：设计令牌 → `ui.div` 布局原语 → kit 组件 → Cutrans 模式组件（`PropertyRow`、`Panel`、`Toolbar`、`ParamGroup`）→ “schema 类型到渲染函数”注册表；另做一个组件画廊页，配合 Tester 与离屏预览。
- **schema 作者一侧**：用 Zig 结构体声明效果器。参数携带稳定 id、label、默认值、合法范围、滑块范围、语义 subtype（不直接点名控件）以及是否为信号参数。comptime 由此派生界面行、MCP `inputSchema`、`.cut` 字段名、校验与文档。排版默认按字段顺序，只有需要时才加稀疏提示（分组、折叠）。
- **与宪法的对应**：[树的声明](04-declarations.md)中的器参二分法（信号参数逐帧消费、可引用参数流；配置参数在产生前只读一次）正对应 AE 和 Blender 中可动画与不可动画的参数之分。schema 必须携带这个区分，界面只给信号参数显示关键帧和驱动控件。

## 用户修正（2026-11-12 同日）

- **现在不考虑版本迁移**。
- **NanoUI 到 schema 的这一层（宿主契约）几乎不应该变化。**
- **插件的 schema 定义一旦更新，就当作一个新插件**，与 VST 插件的行为一致，不做参数迁移。Claude 的推论（待确认）：
  - 插件身份需要带版本，例如 `cutrans.gain@1`；
  - 旧工程继续引用旧插件；
  - 需要的话，宿主可以提供“替换为新插件”的显式操作，而不是静默迁移。
- **排版克制**，参考之前讨论过的“MC 自由，但不会成为编程语言”。
  - 那次讨论的原文**在当前记忆中没有找到**，可能只存在于对话中，或在 [2026-11-11 事故](2026-11-11-incident-recovery.md)中丢失；需要用户复述后补记。
  - 记忆中相近的已有原则：“cut 层牺牲图灵完备换金属性；要计算的逻辑归 `.cop` 原生码”（[泵 分段 1](12-pumps-01.md)），以及“不让 `.cut` 图灵完备”（[哲学散记 分段 5](17-discussion-history-05.md)）。
  - Claude 的理解（待确认）：schema 的排版能力可以给得很自由，比如分组、顺序、折叠、条件显示，但始终只是声明，不包含循环、计算或任意逻辑；需要逻辑的部分由插件原生代码或第 3 层自渲染区承担。
