# 2026-11-08 单一发行入口与虚拟环境安全退出目标

## 用户明确的方向

用户提出并明确要求记录：

- 最终发行应当只有一个 EXE。
- 这个 EXE 是控制启动并进入 Cutrans 虚拟环境／VM 的入口。
- 进入虚拟环境后，内部应有独立的安全退出选项。

这是发行与生命周期目标，不是当前实现或验收结论。本轮只进行架构核对、设计整理和记忆归档，没有修改运行代码、打包产物或安装环境。

## 核心解释：单一文件不等于单一进程

推荐的最终形态是一个公开的 `Cutrans.exe`，由它担任虚拟环境控制入口。VM、Host、NanoUI Shell 与任务执行器的职责和进程边界继续保留，不为了单文件发行把全部业务强行合并进同一进程。

```text
Cutrans.exe
├─ 启动控制器
└─ 不可变载荷
   ├─ Native Runtime
   ├─ VM Pack
   ├─ NanoUI Shell
   ├─ 资产、字体与许可证
   └─ 版本、ABI、清单和哈希
```

对外只有一个入口，不改变 VM 持有文档、资源、授权与任务真源，也不改变 Host 无 Shell 自主工作的能力。

## 启动控制器的目标行为

1. 校验内嵌载荷的版本、ABI、大小、内容哈希和发布签名。
2. 将运行组件发布到受管、按内容版本区分的目录，不使用浮动 cwd 或不受控的临时目录。
3. 对已运行的 Host 检查兼容性与实例身份；兼容则附着，否则隐藏启动独立 Host。
4. 核对 Runtime／Shell、运行用途、分发形态、频道与数据根后，才进入 NanoUI 环境。
5. 启动失败保留旧版本和现有会话，不展示半初始化环境。

相同内容不必每次重新解压；可复用已经校验的受管运行目录。升级通过新目录和原子选择完成，保留旧版本用于回退。用户作品、草稿、任务、授权和 Session 永远不属于可重建程序载荷目录。

哈希用于内容与身份一致性，签名用于发布者身份；嵌入载荷后仍需对最终 EXE 进行发布签名。最终发行验证必须针对同一份 EXE，不能把源码测试或其它构建产物当作它的验收。

## 窗口关闭、安全退出和强制结束必须分开

| 动作 | 目标语义 |
| --- | --- |
| 关闭窗口 | 只关闭 Shell 投影；Host 与后台任务可以继续 |
| 虚拟环境内“安全退出” | 保存可恢复状态、停止业务活动、正常停止 Host，再退出控制入口 |
| 异常／强制结束 | 仅作故障处理；不冒充安全退出，下次启动按中断恢复 |

因此主界面应有独立“退出虚拟环境…”入口，不把窗口 X 改成停止整个 VM，也不要求用户通过普通控制台 `stop` 完成日常退出。

安全退出中的“安全”指持久状态可解释、可恢复，不表示瞬时完成或绝对无故障。未提交草稿仍保留为草稿，不能在退出时暗中提交为正式工作 revision。

## 安全退出状态机

```text
running
  → exit_requested
  → 停止新的 Shell 输入，确认在途草稿
  → Host 停止接受新编辑／新任务
  → 暂停任务调度
  → 保存文档、冲刷已知任务终态
  → 等待或按明确选择取消仍在执行的任务
  → 持久化 stopped
  → 结束 Host 与相关进程
  → 退出 Cutrans.exe
```

执行纪律：

- 活动任务应显示状态，并明确区分“等待完成后退出”与“取消未完成并退出”。
- 取消继续使用现有协作取消；不宣称编码器或 OS 调用可以被强制抢占。
- 排队但未执行的任务不能报告成功，恢复时不能未经核对重复写出。
- 保存、冲刷或停止失败时保留原因，不显示“已安全退出”。
- 超时允许重试或进入明确降级状态；无限等待与直接杀进程都不是正常安全退出。

这里的 VM 是 Cutrans 的声明、文档、资源和任务运行时，不因为叫“虚拟环境”就自动成为 OS 级安全虚拟机。单 EXE 也不自动提供不可信插件沙箱；将来仍需独立进程、最小权限和明确能力口岸。

## 目标实施顺序

1. 先实现安全退出编排和实际场景验证，继续使用当前多文件 Pack，避免与包装改造同时定位故障。

本轮不调整既定下一业务切片顺序：本机文件与资源库薄 App、共享异步求值和缓存生命周期继续按现役摘要推进；本记录补充的是发行与退出目标，不把这些目标提前算作完成。
