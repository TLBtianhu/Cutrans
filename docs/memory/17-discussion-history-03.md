- **懒加载=轮询外包而非轮询消灭(2026-10-14 用户类比立法)**:懒加载的真实收益=**把昂贵的注意力轮询,换成便宜的后台轮询**——让机器/内核/定时器替你盯着,你只管被叫。不是不轮询,是把轮询从主注意力转移到后台机制。类比:眼睛=主注意力(串行、贵、独占),耳朵/触觉=后台传感器(并行、便宜、不占主注意力),它们本身也在轮询,只是轮询的人不再是你。**真正的懒加载=注意力成本转移,不是成本消灭**;只要还有状态变化需要被感知,就得有人/机器去感知,感知=轮询,逃不掉。

- **省力=等待期零动作(2026-10-14 问答:独立泵机器为什么硬件唤醒更省力)**:独立泵机器自己轮询=每次循环都要读游标+比较+跳转,**即使队列空也在做无用功**(持续指令周期消耗)。硬件唤醒(futex/HLT/MWAIT/事件对象)=**零动作**——睡到内核等待队列,从可运行队列摘掉,**完全不运行、不读、不比、不跳、零指令周期**,直到事件发生才由内核放回。省力的本质=**等待期间完全不做事,而不是换一个更高效的方法**;硬件替你盯着,你不用动一根手指。为什么"一定能找到"这种方法?因为 CPU/芯片组早把原语内置好(futex wait queue/HLT/MWAIT/APIC timer),内核也封装好了(futex_wait/event object/condition variable)——你只需声明"我在等什么"(地址/事件),剩下的由硬件和内核包办(按地址哈希的等待桶、中断线直接唤醒),不需要你写任何判断逻辑。**实现路径**:队列空了→futex_wait/事件对象等待→线程睡到内核等待桶,从可运行队列里摘掉(调度器当它不存在)→有新消息→硬件/内核唤醒→线程回到可运行队列,继续处理。等待期间完全不做事,而不是不停地做无用功。

- **空值判别跟写动作走律(2026-10-14 用户立法)**:游标纪律=各写各的(前游标/写游标归产方,后游标/读游标归消费方,对方只读);后游标行动条件=前后相差 ≥1(至少一条可读,不是超过1)。"前游标不动"两情形:写一半(一个 tick 瞬时,release 纪律担保:游标说非空则内容必然已完整)/真没写(绝大多数场景),消费方眼里同义=先别动。**低级判别不是低级轮询泵,是写触发**:产方写内容→推进写游标(对地址的写)→内核在写路径上顺手查等待者(futex_wake/SetEvent)→唤醒消费方。**空值判别跟着写动作走不跟时间走——只在答案刚变的那一刻被问一次,消费者从头到尾零扫描,低级层也零扫描**;高级泵的判别(解析/理解/执行)只在被唤醒后启动。懒触发便宜的真正根源=判别挂在事件本身上,谁也不周期性地问。

- **游标相等≠撞车(2026-10-14 问答澄清)**:环队列两不变量——读侧 R≤W(读游标永不越过写游标,不能读没写的)/写侧 W−R≤N(写游标永不套读游标一圈,不能覆盖没读的);**R==W=空,合法常态;W−R==N=满,合法常态;都不是事故**。真撞车只有两种:R>W(读了没写的)与 W−R>N(覆盖了没读的)。"读完推进"的正确协议:推进前查 W−R≥1(至少一条可读),读完推进到 R+1——允许 R+1==W(只是刚读空),下次 W 前移又可读。误读纠正:推进后相等不是撞车,是空。

- **空即睡写即醒,无低级泵律(2026-10-14 用户立法,我修正"低级硬件泵"想象)**:模型形状=R==W(读游标指向空槽)→停高级泵(睡);写发生→醒接着跑。**但不存在低级硬件泵在检测**——高级泵睡=futex_wait 挂进内核等待桶从可运行队列摘掉,零运行零扫描;唤醒的触发器=**产方写路径本身**(写内容→推进写游标→futex_wake/SetEvent 顺手查等待桶→放回高级泵)。**检测器不存在,触发器就是写者本人**;空值判别只在答案刚变那一刻执行一次,执行者是产方写路径不是某台轮询机器。省力根源终版:等待期间系统在这件事上做的是**零**,不是"很少"——懒触发便宜的真正根源=判别挂在事件本身上。备注:多消息时醒来的泵抽干到 R==W 再睡;最底层硬件的连续守望(比较器/tick)归轮询守恒律管,OS/软件栈这一层是纯事件触发连 tick 都不用。

- **低级泵的真身律(2026-10-14 问答立法:"低级泵"有多低级什么原理)**:底层确实有东西在看没有魔法,但最低级的**不是泵是判决器**。中断线→CPU 的三层守望:①**比较器(电平守望)**——模拟电压判决,输入差过阈值输出翻转,一直在看但无循环无取指无 tick,是物理现象(晶体管传输特性)非泵,**最低级=连续场判决**;②**沿采样器(触发器)**——比较器输出由触发器在时钟沿锁存进中断挂起位,**主从锁存对把连续守望裁成沿上采样,这才是最低级的泵(tick 粒度轮询)**;③**指令边界查挂起位**——CPU 每条指令退休时查一次,指令粒度轮询(轮询守恒律的 CPU 内现身)。再上:futex 等待桶=零轮询(检查挂在产方写路径上,写发生才查一次);调度器看不见睡的线程(不在可运行队列)。**"睡"的精确化:从可运行集合里除名,由写者在写路径上重新点名**。所以用户直觉对大半:底层确实有守望,但形态=比较器守望+沿采样,不是循环泵——**泵的最低形态=沿采样器,比泵更低级=比较器(连续场判决,不是泵)**。

- **睡到地址被写而非睡到谓词(2026-10-14 问答:低级泵的调用形态)**:用户设想的"if 空则 sleep,continue 条件=非空"形状对,但三点拧紧——①**睡法=睡到地址被写**(futex_wait(addr, expected):值还等于 expected 就别让我跑),不是睡到谓词;内核管"变了",你管"对不对"(醒来自查业务条件);②**必须 while 复查不是 if 单判**(唤醒只代表发生过写,不代表轮到你有份——多产多消/虚假唤醒边角;形态永远 while(空){futex_wait});③**查与睡之间的竞态窗由两参数堵死**(futex_wait 原子语义=值若已变就不睡,产方在你查完刚要睡时写进来也漏不掉)。**泵的调用形态**:每 tick 发现 R==W→记快照→futex_wait(&写游标,快照)→睡(从可运行集合除名)→产方写+推进游标+futex_wake→被点名→while 复查→消费到 R==W 再睡;Windows 同款=事件对象 WaitForSingleObject/产方 SetEvent。启动器直调阶段没有环,此条=树泵/工作泵时代的施工图。

- **R==W 优于 W==空(2026-10-14 问答:两种空判哪种好)**:R==W=游标比较(一条整数比较,不解引用槽位),W==空=内容检查(要钦定哨兵值占内容空间+读槽位+自带竞态——读完到行动间内容可能被产方改掉)。**用户担心的"指令写到一半"由 release 纪律消灭**:先内容后游标——游标一旦动了内容必然完整,写一半时游标根本没动,R==W 依然读作"没有完整的可读项";**写一半的指令对读者永远不可见,读者世界里只有"没写"和"写完",没有"写一半"**(游标=发布点,中游写状态被挡住)。白送的好处:R==W 的检查直接就是 futex 的睡觉地址——睡到 "&W 被写"(产方推进游标就是写它),**判别式与等待地址一物两用**。

- **覆写即清理律(2026-10-14 用户立法)**:定长环里槽位的死亡=**套圈覆写**,不做显式 clear。时间+空间双收的根因=**空间早已付账**(容量申请时就给了):clear 不回收任何空间(还在预留里),纯浪费一次操作;覆写本来就要写,零追加成本,还白送**最近一环的免费缓存**(消费过的最近 N 条还在环里——命令环的日志热尾,调试/回放/审计开箱即有)。硬盘粉碎同构:文件系统删除=打标记,内容留到被覆写(forensic 能恢复近期数据正因这个);**删除是元数据动作,覆写才是真动作**。边界:含安全语义的内容例外(密钥/凭证显式清零,归凭证不动律管),命令环良性默认不清。与游标单调律合流:游标单调前进,环=无限流上的滑动窗,流永不缩窗向前滑。

- **自声明=为不确定性付的税(2026-10-14 用户立法)**:读者的能力不被上下文确定时,数据必须自己开口——类型标记/WAV 头(采样率点数)/文件后缀名(用户 OS 看后缀决定用什么读)=**为不确定性付的自声明税**;"定长"的真身=**能力被上下文十分确定时不用任何自声明**(读者翻开先验直接读,零税)。
- **定长类型结构=定义一种新的进制(2026-10-14 用户立法)**:结构体=一套数制(定死数位/数位含义/进位方式),故有金属感;只靠定长不够用的两因:进制小了描述不全,进制大了必然浪费(人的数据分布在长度上不是定值——同一文件夹里文件大小参差不齐);**正确形态永远三段式:定长最小单元(物理结构)+变长数量(认知形态)+一次性长度声明(头/先验)**。哈希值那点=人认知模型要的空间是哈希值那么薄,但数据最大占用又可能那么大——定长只能要么截断要么浪费,所以"定长最小单元+变长数量"必须成立。
- **长度信息的三种付税形态(2026-10-14 立法地图)**:变长编码核心难题="描述重复次数的数字怎么不和数据混为一谈",全世界只有三种付法——**零税/先验确定**(寄存器布局/结构帧:零成本,条件是读者能力被上下文钉死);**块头税/声明位**(WAV 头/图片 u32×u32/zip 文件头:一次性头开销,读块前读头);**逐位税/自同步判别位**(UTF-8 续位标记/熵编码:每单位 1/8~1/4 开销,无先验也要能找边界)。**zip/7z/熵编码=逐位税的极端形态**:每一位的意义由上一位/概率先验决定——先验头短到近零,空间利用率顶到信息熵极限,但**随机访问死/对齐死/硬件先验全废**,省的是空间付的是"以后每次读都得从头解码一遍"。
- **我们的落点**:块头税+先验混合——声明层存裁剪范围(一次性元数据,给 UI),cap 制式缓冲先验定死(给计算),地址不动;逐位税只在"必须无先验自同步"的场景(压缩包/网络流)才付,而且那是 codec 插件的事,不进核。

- **RNA 推导链(2026-10-14 从零推导 Blender 不用写字段代码的原理)**:推导八步——①文档=C 结构体树(数据);②需求=人要能看能改字段;③笨办法=每字段写 UI 代码(不可扩展);④**关键洞察:控件是字段类型决定的,不是字段身份决定的**(float→滑块,enum→下拉,color→取色器,bool→勾选,pointer→选择器,**所有 float 共用同一滑块代码,所有 enum 共用同一下拉代码,控件按类型复用不按字段定制**);⑤SDNA 白送类型表(每个结构体的字段元数据);⑥**RNA=SDNA+访问函数(getter/setter)+UI 提示(min/max/default/tooltip)+路径字符串**——运行时属性注册表,文档每个字段在这张表上有完整档案;⑦**通用控件引擎**:"给我一个 RNA 路径和一个矩形,我查类型和提示,画出对应控件,绑读写"——几千个字段共用十来套通用控件代码,新加字段只在 RNA 注册类型和提示,零新增 UI 代码;⑧Python 声明式 UI:layout.prop(path)——面板代码=声明要什么不是实现怎么画。**用户猜测修正**:"同一套 UI 风格"只对了一层皮——样式引擎管"长什么样"(颜色/圆角/动画),**类型调度管"该用哪种控件"**(float 用滑块/enum 用下拉/color 用取色器),两个正交轴;不用写字段代码不是因为大家长得一样,是因为**每种控件类只写了一次,几千个字段按类型被分发到那十几种控件类上**。全管道:文档→RNA 元数据表→声明式面板(路径)→通用引擎(类型分发)→样式引擎(皮)→像素。**对我们宪法映射**:RNA=命令注册表(opcode→handler 表,同款)/通用控件引擎=node.zig 走树(记录类型派发画笔)/样式引擎=widgets.zig 主题/声明式面板=pages.zig 声明树。**真身:RNA=文档结构的运行时元数据表,UI=类型驱动的通用引擎+声明式路径绑定——样式引擎只负责皮,类型调度才是不写字段代码的根**。

- **没有 RNA 会怎样(2026-10-14 反推立法)**:RNA 本质=**一张运行时元数据表**,没有它四类消费者全退化成"每字段写定制代码"——①UI 面板=每字段手写一行 uiDefButR(block, 类型, 名字, &字段, min, max),几千行,新加字段=再来一行,改类型=找出所有这行改掉;②序列化=每结构体手写存读函数(save_scene/write_int/…),改一次结构体改一次序列化器,旧文件打不开(没有迁移元数据);③脚本=每个可访问字段手写 C 包装函数(get_res_x/…),要么写几千个绑定要么放弃脚本;④动画=没法按路径动画任意属性,只能硬编码"哪几个字段可动"。**RNA 的四样加法各挡一种定制**:类型表(SDNA)→挡序列化定制;getter/setter→挡读写定制;UI 提示(min/max/default/tooltip)→挡控件参数定制;路径字符串→挡动画/脚本寻址定制。**有了表,UI 引擎/序列化器/脚本引擎/动画系统全变成查表的通用引擎——新加字段只在表里注册一行,四类消费者自动全会**。与我们中转站化归律同形:n 字段×m 消费者各自定制=n×m 乱麻,RNA 把它压成 n 个注册+m 个通用引擎=n+m;我们的命令注册表(opcode→handler 表)是同一个形状:没有注册表,UI 控件就得直接调处理函数(硬编码),有了注册表,一切走名字查表通用派发。

- **Blender UI 代码四问诚实评(2026-10-14)**:①独立一块?——**概念上可分形状,实际上拔不出来**:interface/(ui.c/ui_block.c/ui_but.c/interface_widgets.c/handlers/draw)与 RNA/context(bContext)/G.main/GPU draw manager 深度焊死(控件全绑 RNA,事件全读 context,绘制走 Blender draw manager 非裸 GL),有人试过抽成库结论=它是"Blender 的 UI 工具包"不是"一个 UI 库";②逻辑跟风格强绑定吗?——**部分解耦**:面板声明"画什么"(逻辑)与引擎"怎么画"(渲染)分开,但**风格是 C 硬编码非数据驱动主题**(控件颜色/圆角/悬停效果全在 interface_widgets.c 里 C 写死,不是一份主题数据表;有用户偏好主题色系统但控件形状和行为是代码写死的)——**我们的 theme.zig 在这根轴上反而比它更解耦**(主题=数据,控件=模板);③代码量?——**不小,是台大机器**:interface_widgets.c 单文件 5000+行,ui_block.c 三千行,加 handlers/templates/draw/icons,interface/ 目录=几万行几百种控件的全套立即模式工具包(按钮/滑块/文本框/颜色选择器/曲线编辑器/弹出层/菜单/提示框/搜索框),不是精简核是台成熟复杂的大机器;④**对象编辑态度 vs 我们泵机器态度(最大分野)**:Blender=**单泵全局文档**(G.main 全局单例,主线程独占一切编辑,操作符系统主线程同步跑,场景变更走 depsgraph 按需重算;并发只给后台任务渲染/烘焙且有严格"不许碰场景"纪律);我们=**多泵 per-comp**(每合成一台独立泵机器:自己的泵+自己的唯一帧,命令环喂树泵唯一串行化点,以查代算版本化缓存);Blender 的合成器(CompositorNodeTree)反而接近我们模型(节点树按需缓存评估),但场景编辑是单泵全局文档,和我们"一切皆插件每合成一泵"是两条路;⑤布局代码能不能直接复用格式?——**代码不行**(与 context/RNA/scene/GPU 焊死,复用格式=复用 RNA+context+G.main,正是我们不要的全局单例/C API 蔓延);**模式可以,而且我们已经在用了**(声明式属性路径 layout.prop/类型分发控件/operator 命令/poll 门控/注册扩展——我们已在命令注册表+声明式 pages.zig+node.zig 类型派发里复用;它的渲染代码 interface_widgets.c 换我们的 wgpu_imgui+theme.zig)。**总评:它不是一块能拆走的 UI 库,是一台与 Blender 本体焊死的大机器;模式值千金(已在用),代码一文不值(焊死带不走)**。

- **一切皆插件与每合成一泵的可行性三样本(2026-10-14)**:①**DeepSeek Harness**(DeepSeek AI 开源 agent 运行时,内核 Cordis,slogan"Everything is a Plugin",CLI=dsh,Node.js)=**Cordis 极简内核只管插件注册表+生命周期,其余全部(模型/工具/技能/会话/沙箱/存储/循环/调度)皆是插件**——一切皆插件在 agent 层已证可行;**关键观察:它的"一切皆插件"不是"每插件一泵",插件是挂在 Cordis 共享循环上的能力(能力注册),不是每个插件各自带泵**。②**MC/JVM 模组**=Java 类被 Forge/Fabric 加载进同一 JVM 同一堆同一条游戏主循环,模组无自泵只是注册到注册表/事件总线上的事件处理器——**一条大泵+事件总线+模组即处理器,单文档模型(一个世界)配单泵注册**。③**我们每合成一泵**=多独立文档(合成)→每合成一泵,可行真正原因=**闲置泵几乎免费**(futex 睡死零 CPU 零调度,一泵只占几 KB 栈+内核结构;100 合成=100 睡死泵,只有被预览/渲染的那一两个在跑;成本=活跃泵(少)×计算+闲置泵(多)×可忽略)——**它成立是因为大多数泵大多数时候是闲的,不是因为插件都要泵**。~~**和解(别让两法打架)**:早法"环按职责分不按 comp 分"与新模型"每合成一泵"的和解=每合成一泵=评估/失效层的轻泵,重计算=共享工人池~~(2026-10-14 用户纠正:**和解不必要,徒增规则**——模型自洽:闲置泵睡死免费,活跃泵由预览需求天然限流(通常一两个),批量导出时 **OS 调度器本身就是那个池**(时间片轮转),立规则立一个池=给已存在的池又立个池;我把别处游戏引擎工人池模式当解药搬来,我们的模型根本不生病;真正的工人池该出现的唯一地方=**单个大效果器自己 tick 内的计算策略**(SIMD/GPU/内部线程池并行一个特大卷积),那是每效果器自选不是拓扑规则)。**教训:规则要为模型服务,不是为别处的好看家法服务;模型自洽时,最好的立法就是别立**。**结论:"一切皆插件"已被 DeepSeek Harness 证明可行(且不必每插件一泵);"每合成一泵"在我们多独立文档模型下也可行(闲置免费),但要与重计算分家。用户担心可行性,本质不是"插件能不能都是泵",而是"独立文档配不配各自带泵"——配,因为闲置免费**。

- **泵的粒度决定栈的角色(2026-10-14 用户立法)**:泵范围=单函数/单消息→栈=该函数解析的**隐形暂存**(一进一栈律,外不可见,烧录在函数内部);泵范围=模态级(多插件多函数)→栈=**插件间调用的连接件**(A 压栈调 B,B 的整棵子树得先算完 A 才续——**头行阻塞+状态互嵌,不灵活**;用户担心完全成立,前提是模态泵用共享 OS 调用栈做插件互调)。**两条出路**:A=泵粒度降到 comp/函数级(栈回归隐形,一进一栈,每个 comp 自己的效果树内部嵌套,comp 间走通道帧 id);B=**续体/微栈模型**(模态级单泵但不给插件共享大栈,给每个异步流程发自己的续体 continuation——Node.js async/await 干的事,也正是 dsh 的形状能推出的关键机制:dsh 插件=async 能力,await 让每个逻辑流程自带 continuation 状态机(promise 状态)而不是往共享 OS 栈上压帧,事件循环调度这些续体,插件 A await 插件 B=续体链不是共享栈帧,所以 dsh 能在一个事件循环上让插件互调而不被"大栈归统"——**它把用户的担心用续体化解决了:栈没有被消灭,是被切成了每个流程自带的小栈状态机,不再有"一台大泵一根大栈管所有插件"**)。**对我们宪法的落点**:comp 泵内效果器组合(子效果)=栈一进一栈栈在 comp 内隐形;comp 泵间=通道帧 id 绝不走栈;将来我们自己的 agent loop=Node 续体模型参照系(工具调用走续体/命令环,不该走一根共享大栈把插件全串起来)。**边界声明**:dsh 的内部线程/泵粒度我只有公开形状(Cordis+插件+Node.js+dsh CLI),没有可靠到内部泵怎么分的细节,以上 B 是从它是 Node.js agent runtime 的形状推出的机制,非内部实证。

- **续体=便签而非工位(2026-10-14 用户问答立法)**:续体(continuation)=**把"接下来要做什么"从 OS 栈上卸下来打包成堆里的状态机,事件到了再由事件循环恢复执行**。比喻:线程=人占工位等电话(工位=OS 栈全程被占哪怕干等);续体=写便签"我停在 42 页 3 列"让出工位,电话响回来照便签接着干(工位=事件循环那根线程空出来,位置=便签状态机非工位)。**async/await 的 await 本质**:函数执行到 await 挂起——局部变量+执行到哪行被打包成续体对象(promise 状态机),OS 栈当场释放,事件循环跑别的,结果到了从断点接着跑;"接下来要做什么"不再是栈上返回地址而是堆里的状态机。**与多泵的本质区别**:多泵=每个执行上下文各占一根 OS 栈由 OS 抢占调度;续体=同一件"剩下要算的事"被切成堆里的状态机由事件循环协作调度——一个占着工位等电话,一个留张便签让出工位。**频谱**:OS 线程(重栈 OS 调度 ~MB)→goroutine(小可长栈 Go 运行时调度)→续体/无栈协程(纯状态机事件循环调度 ~字节;C++20 协程/Rust async/Zig 在做的 async/Lua 协程/Python asyncio)。**解"模态泵大栈归统"的担心**:不用共享大栈也不用每插件一根 OS 线程——每个逻辑流程发一张便签(续体),事件循环在一根线程上 multiplex 几千个续体;插件 A await 插件 B:A 挂起(便签存好),B 跑,B 完,事件循环把 A 的便签捡回来接着跑,**共享 OS 栈在 await 期间是释放的**——插件互调既不占大栈也不占线程(dsh=Node.js 能在一个事件循环上让插件互调而不僵死正因这个)。**对我们落点**:comp 泵内=comp 级线程泵栈在 comp 内隐形(一进一栈);将来 agent loop=工具调用走续体模型(每流程一张便签,命令环当事件循环),不走一根共享大栈串所有插件也不给每个工具发 OS 线程;Zig 的 async(正在重做)=无栈协程=续体,将来可手写状态机续体。

- **续体 vs 多泵=两个调度域不是优劣(2026-10-14 用户挑战修正)**:用户指控"续体=用户态重造 OS 线程的轮子且舍弃多泵虚拟化便利"——**成立一半**:①概念上续体确实就是用户态线程(协程/绿色线程/纤程全是把 OS 干过的调度在用户态又写一遍,事件循环调度器=用户态写的小 OS,"自己写轮子"成立);②丢的便利是真的——**抢占公平**(OS 公平切片,事件循环协作式,贪心续体永不 await 就卡死整个循环,Node.js CPU 密集卡死事件循环就是这个病)、**真并行**(多线程同时在多核,单事件循环=单核除非开多循环)、**调试性能分析**(OS 线程有干净栈可查,续体的"栈"是状态机难检查)、**隔离容错**(线程崩了能圈住,循环里未捕获异常能带走整个循环);这四条全是 OS 多泵的虚拟化便利,续体全丢,是设计上的舍弃不是疏忽。**另一半"没有运行原理的区别"=错**:区别恰恰在运行原理——**调度者不同**(内核抢占式=系统调用+TLB/缓存冲刷的上下文切换贵 vs 事件循环协作式=函数调用成本切换无内核陷入便宜)、**占用不同**(~MB 栈+内核结构 vs ~几百字节状态机)、**并发模型不同**(共享内存+到处要锁,抢占逼的 vs 单循环协作=循环内零数据竞争不用锁);一万个并发工具调用/网络等待:一万根 OS 线程=几十 GB+调度爆炸,一万个续体=几十 MB+函数调用成本切换,**内存差千倍切换差几个数量级**。**诚实结论=调度域分工**:IO 密集流程极多要锁少(agent loop 成千上万个等 LLM/网络/文件 IO)→续体赢(成本+循环内无锁);CPU 密集要真并行要抢占公平要隔离(comp 渲染大计算)→OS 线程赢别自己写轮子。**现代运行时真实形态=混合:事件循环跑 IO 续体,工作线程跑 CPU 任务——不是续体取代线程,是各守其域**。教训:之前说"续体解大栈归统"说得像它普遍更好,不准确;准确版=续体和多泵不是优劣是两个调度域,别用续体做 CPU 密集并行(拿用户态轮子硬碰 OS),也别用 OS 线程养一万个 IO 等待(拿 MB 栈换字节便签)。

- **续体的两个具体场景(2026-10-14 用户问答)**:①**agent loop(我们的将来主场)**:一个 AI 会话流程=收到命令→调 LLM(等 API 回包 ~3s)→LLM 说调工具 A→调工具 A(等 ~1s)→再调 LLM(等 ~3s)→调工具 B(等)→最后调 LLM(等)→出结果,**全程 ~8s 里 ~7s 在等只有 ~1s 真在算**。线程版=每会话一根 OS 线程,每到"等"阻塞在线上,一千并发会话=一千线程×~MB 栈=几 GB 内存,且 90% 时间在睡还得调度(内核陷入+TLB 冲刷);续体版=每会话一个续体对象,每到"等"挂起,续体存={我现在在第几步/局部变量(命令原文+已收集结果)/我在等哪个事件 #id},OS 栈当场释放事件循环去跑别的,事件到了把 #id 的续体捡回来从断点接着跑,**一千并发会话=一千个续体对象(~几百字节)=几十 MB,全 multiplex 在一根事件循环线程上,等待期间 OS 栈释放谁也不占工位**;②**NPC 过场脚本(最直觉)**:脚本"走到 A 点→等 2 秒→播放音效→等玩家靠近→说台词",写成线性 async 代码 await walkTo(A)/await sleep(2)/playSound()/await playerNear()/say(),每个 NPC 的脚本=一个续体(走到一半挂起存"我在等 walkTo"/睡到一半存"我在等 2 秒"/等玩家靠近存"我在等 playerNear"),**几百个 NPC=几百张便签,游戏主循环一根线程全带,不用每 NPC 一根线程**。**两个场景续体赢的三条件全中**:等待占大头(IO/定时器/事件不是计算)/流程数量大(上千会话或 NPC)/流程间要互调(要锁少)——线程在这三条件下又贵(MB 栈)又要锁(抢占)。**反面:comp 渲染不用续体**:计算占大头(效果器真在算像素不是等)+流程少(几个合成)+要真并行(多核同时算)——三个条件全是线程主场,comp 级线程泵算重活,续体"省等待"的好处用不上(没多少可等的)反而丢了抢占公平和真并行。**一句话:续体主场=大部分时间在等流程一大把;线程主场=大部分时间在算要真并行**。

- **MC 模组为什么线程续体都不用(2026-10-14 用户问答立法)**:**根因=MC 的世界是"单写者 tick 原子"文档**:每 tick 世界所有东西按固定顺序在主线程上同步更新一遍,**世界的一致性依赖"一切都在同一拍内顺序发生"**——模组跑独立线程(会跟主线程抢世界状态要锁)或用续体(在 tick 中途挂起回来世界已被改)都破坏 tick 原子性,所以一个都不许用。**表因=模组处理器是"跑完即回"的短回合**:方块破坏/物品使用/实体 tick 处理器微秒级跑完就返回,**既没有 LLM 那种"等 3 秒 API"的可挂起点(续体无处可用),也没有"要并行算一堆像素"的重活(线程无处可用)**——续体赢在等待多,线程赢在计算多,MC 模组处理器等待和计算都几乎没有,两种策略对它都是无的放矢。**MC 的异步/重活在引擎内部刻意与模组世界隔开**:区块生成/加载/网络/部分渲染用线程但住引擎内部,不暴露给模组 API;模组写"方块/物品/机制"这种活在同步 tick 里的内容逻辑,需要长耗时活的模组走专门异步 API 把活排到 tick 外,边界画清。**这正是一进一栈律的最大规模实证**:MC 每个模组处理器=主泵上一个完整栈回合(一事件=一回合跑完即回永不交错),主线程=树泵唯一串行化点,模组通过事件注册喂给它——**模组作者永远不需要锁,不是 MC 有魔法锁,是一切逻辑天然在同一根主泵上顺序跑,抢占和共享从定义上就不让它出生**。**调度域分工闭环三负载三答案**:dsh(agent loop)=IO 等待占大头流程上千→续体(便签不占栈)/我们 comp 渲染=计算占大头要真并行→线程泵/MC 模组=单写者 tick 原子世界处理器跑完即回无等待无重活→都不用主泵顺序跑完即回——**当世界模型是单写者 tick 原子时,最优解是既不加线程也不加续体,把一切摁在一根主泵上顺序跑,锁和挂起这两个问题从定义上就不让它出生**。

- **UI 游刃有余六层栈(2026-10-14 综合立法,Blender 模式装我们宪法地基)**:①文档树(工程数据+UI 状态+上下文,都是树都是 id);②**属性注册表**(路径→{类型,提示,getter/setter},RNA 同款元数据表,让通用控件/序列化/脚本/AI/动画全免费);③**操作符注册表**({名字,参数模式,poll 门控,处理函数},命令=可类型化可调度的操作,UI/CLI/AI 同名同参触发);④**声明式面板**(页面声明"显示哪些路径+布局提示",不声明怎么画);⑤**通用控件引擎**(类型分发控件模板:查路径→查类型→实例化→绑读写)+主题(纯数据);⑥输入翻译(指针事件→命中测试→翻译成"调哪个操作符+什么参数")。**一句话核心:UI 不写控件代码写属性路径,不写处理逻辑写操作符,不存控件对象存声明和数据,不画状态投影状态**。四铁律:UI 只是操作符的一个触发器(无特权逻辑)/一切是数据(文档/UI 状态/页面声明/注册表全是树或表,每帧按声明+文档状态重建,不存控件对象不写失效通知)/可见可用=poll 谓词对上下文求值非写死布尔/通用优先于逐字段(控件绑路径不绑变量,新字段注册一行就能上 UI 零新增控件代码)。**我们现有代码逻辑四宗罪**:①数据是页面手动塞给控件的(pages.zig 把字符串当参数递控件,控件是哑的——应该控件拿路径自己去注册表取 listItem(path="projects[0]"));②状态是散装全局变量(search_buf/status_buf/page 裸全局无上下文树,没法序列化没法给 AI 读没法做选中态——应该一个上下文树,页面切换/搜索词/选中项全是树里 id 节点路径可寻址);③命令只有名字没有参数模式和门控(Action 就一个字符串,表达不了"工程加载后才可点"和"以 1080p30 导出"——操作符必须{名字+参数模式+poll+handler});④静态树给动态内容判死刑(comptime 常量树写死两条示例,真从磁盘读 40 个工程一条都装不下——需要 repeater 节点:声明"对 projects 每一项重复一个列表项",每帧从注册表读数据投影成条目)。**别动的对件**:立即模式语义+声明树/主题=数据控件=模板/命令注册表汇合点/泵归我们不归库。**编辑空间外推**:Blender 三级容器(Workspace 工作区切换→Area 平铺区预览/时间线/检查器/素材池各住一个编辑器实例→Region 区内子带标尺/轨道/工具条),布局=**平铺骨架**(共享边拖边同缩伸拖合并删边,运行时数据非编译期死树,用户可拖任意布局骨架保证无缝无重叠),素材池类面板=repeater over 文档(project.media 每项→一个条目控件绑属性路径,数据变条目自动变因每帧按声明+文档重建)。**最好答案一句话:把 Blender 的 operator/RNA/poll/声明式/注册扩展那套模式装在我们自己的树+id+泵宪法上,扔掉它的 G.main 全局单例和 C API 蔓延——文档是树不是单例,状态是树不是散装全局,操作符带参数模式和 poll,面板声明路径不实现控件,动态内容走 repeater 投影,编辑空间用平铺骨架**。

- **UI 布局=MC 模式(2026-10-14 用户立法,沙盒类比)**:MC 在游戏界自由**不是因为能写代码,是因为不让写代码只给三样**——方块库(先验强封闭机制集,你选不写)、摆放(放哪放多大,仅有的自由参数)、红石(有限逻辑系统,简单到"玩"不是"编",但够把方块连成机关)。**自由度的真相:不是"能造任何东西",是"机制库富到靠选和摆就能拼出 99% 想要的";给代码编辑器就变成编程任务,自由反而死了**。**套到 UI 布局一一对应**:方块库=控件块库(按钮/滑块/输入框/列表项/卡片/胶囊/表格/树/图标,封闭先验集行为已定);摆放=布局声明(画布上的位置+尺寸=仅有的连续值);红石=有限逻辑系统(**属性绑定(路径→控件)+poll 谓词(简单布尔)+操作符参数+布局提示**——UI 的红石,只能接线不能写函数);机制归引擎(绘制/命中/动画/派发,引擎一次写好之后永远只被选用)。**组合配方对应**:MC 方块摆一起出熔炉红石电路;UI 控件摆一起出搜索框(输入+按钮+列表)/设置行(标签+控件)/主从视图(列表+检查器)——**功能从摆放里长出来不从新代码里长出来**。**最值钱一句:自由来自约束**——UI 逻辑本来就稀疏(显示这个/绑那个/满足条件才可点/跳到哪),稀疏到"选"就能表达,所以不该给代码,该给一个富到能选遍的机制库。**边界丑话:红石必须有限**——一旦布局里能写循环/条件/自定义绘制,设计师退化回程序员,MC 的简洁就没了;逻辑系统只许**绑定/谓词/参数**三样,要循环/自定义绘制就去引擎层写一个新的控件类型(那是"机制扩展"是另一个动作,归引擎不归布局设计)。反例:web/electron 能写任何东西→变编程任务失去设计感;纯 ImGui 代码驱动→是编程不是玩 MC。Blender 活样本:标准面板全是 layout.prop 声明(选),Python 只在要扩展机制时才出场。

- **渲染画面=声明结构帧与 UI 渲染四律(2026-10-14 用户立法)**:①**当前渲染画面声明结构帧律**:当前显示什么记录成**声明结构帧**(哪些画布/面板/控件+布局参数,全是声明没有一个像素)——UI 状态=一小棵声明树,渲染=UI 渲染引擎解释这棵树出像素(怎么变成画面归引擎不归帧);②**一树两读者律**:文档结构帧被两个读者读——合成器读它当计算输入,显示路径读它当可显示参数,**不用专门给每个结构帧设计 UI**;中间过一层**显示策略**(结构类型→控件呈现方式的映射表:饱和度字段→滑块/颜色字段→取色器/枚举→下拉,即 MC 模式"红石=绑定"的落点,是"文档是数据"和"怎么给你看"之间的桥),UI 渲染引擎作用在显示策略帧上不直接啃原始文档结构;③**输入/渲染两回事律**:**屏幕交互改结构体参数**与**结构体参数变动引起渲染变动**是两条独立流向,中间隔状态——输入事件→命中测试→调操作符→改状态(文档树),渲染画面←引擎读声明帧+文档状态←状态变了引擎下帧重建;**不是"输入→直接改画面",是"输入→操作符→改状态→状态投影出新画面"**,输入事件永远不许直接碰渲染只能经操作符改状态,画面跟着状态走;④**点击检测归专门引擎**:命中测试是独立引擎(指针位置→拿当前声明帧布局几何→查坐标落在哪个声明节点→翻译成"调哪个操作符+什么参数"),渲染引擎管画检测引擎管点各管各的,控件不自己手写命中。

- **树按写者分家不按读者律(2026-10-14 用户立法,统一"本体编辑 vs 为 UI 而生"的乱)**:乱的真病根=**按读者命名树**("UI 树"/"内容树")——渲染参数帧像本体编辑因它有两个读者(合成器+UI 引擎),启动器布局帧像专为 UI 而生因它只有一个读者(UI 引擎);**但"有几个读者"从来不是树的属性,是读者的分布**。统一模型:**树=数据,归属=写者,用途=读者**——渲染参数帧(内容树:写者=操作符,读者=合成器+显示策略)/启动器布局帧(本体性树:写者=启动器自己,读者=UI 渲染引擎)/显示策略声明帧(本体性树:写者=显示策略机,读者=UI 渲染引擎)/UI 引擎状态帧(本体性树:写者=UI 引擎自己,读者=显示器=物理世界)。**"UI 树"这个类别不该存在**——没有哪种树是"UI 树",只有"被 UI 引擎读的树";启动器布局帧不是"为 UI 诞生"的特殊帧,是启动器这台机器的本体性树(它写自己的界面状态)恰好被 UI 引擎读;渲染参数帧的 UI 显示也不是添头,是内容树的第二个读者,和合成器平起平坐(都读同一棵树,各取所需:合成器拿去算,显示策略拿去画)。**乱的根源=把读者当成了树的种类;改按写者/角色分类,所有树瞬间归位:要么是谁的本体性树(某机器自己写的状态),要么是内容树(文档数据),没有第四类,没有"为 UI 而生"的怪胎**。

- **树=装配蓝图唯一读者=装配器(2026-10-14 用户立法,纠正"树"的角色错位)**:树的引用逻辑(节点→节点)与变长结构是两个维度,且**树的引用有且仅有一个读者=装配器**——独立泵模型下运行期没有树要遍历:合成机 A 引用合成机 B 的输出帧用**机器 id**,而这个 id 是**装配期**装配器读蓝图时解析好写进 A 的记录的,运行时 A 按解析好的 id 直读 B 的帧永远不回树里走;**树的存在域=装配期(+序列化到 .cut),运行期没有树只有解析好的 id 和帧,树的全部工作=被装配器读一次然后消失**。"树不能被计算类合成器直接用"=结构事实非感性:合成器读密集帧按 id,树是装配器的图纸。**蓝图乱感的来源**:每节点塞三样(什么机器+怎么接线+什么参数)其实不乱——三者同寿命(全编辑期设定全序列化全声明),乱的错觉来自把装配期(蓝图被读)和运行期(帧对帧流动)混成一团;**蓝图只管装配,运行期只管帧流,两条时间线不碰头**。
- **蓝图本质=机器清单+接线关系,容器形状无所谓(2026-10-14)**:正序=**先定结构帧(数据基元),后定蓝图(装配描述),树只是蓝图的惯用容器**;蓝图装成树只因合成可嵌套引用合成,但实质是清单+接线,编译成平表(机器表+id 引用列)一模一样。**基元是结构帧不是树**——前阵子树谈得多是因启动器 UI 树和合成树霸占议题,不是树是基元。
- **结构帧定长律的精确版(2026-10-14 问答)**:结构帧 schema **永远定长**(读它的机器要常数时间解析——定长金属感律,字段变长=解析带逻辑递归=金属感死);**"尺寸"可以是数据**(图片 1920×1080=声明层参数写在结构帧里当值,裁剪范围=声明层元数据,变长=声明可变地址定长律:改声明不改地址);**数量可变靠定长单元重复不靠结构变长**(帧=像素×w×h 像素定长数量随尺寸,蓝图=记录×N 记录定长数量写头)。**三段式永远成立:定长最小单元+变长数量+一次性长度声明**;连装配蓝图自己都服从(记录定长/数量变长/数量写头)。

- **变长不住结构维住数量维律(2026-10-14 用户以UI排版/MC地图逼问定长律后立法)**:不立"定长结构帧/变长结构帧"两个并列概念——**"变长结构帧"物理不存在**;世上所有号称变长结构的东西只有三种真身:①**定长单元×变长数量+头部长度声明**(数组/字符串/链表/树/MC地图/UI文档);②**定长头+不透明体**(TLV/带tag联合:tag+len在固定位置,体只有认识tag的读者解析而它看到的是该类型的定长schema;ccb的len是给不认识者跳过的);③**序列化/压缩blob**(存储税,加载时付清,落地即定长)。**没有第四种**;原因:寻址要求内容被解析前长度已知→长度必须住固定位置头部→**schema定长是寻址的前提不是风格选择**,字段级变长=读者跑逻辑才知下一字段位置=解析带递归=金属感死。要区分的是两个**槽位**不是两种帧:**结构帧槽**(合成器输入输出/活的数据实例,永远定长schema,尺寸可当数据写进帧)vs **文档/集合槽**(蓝图/.cut/UI声明树/MC地图,定长记录×变长数量+头部声明);一切"没法定长"的场景真身都是文档槽(数量无界),而文档槽被三段式收编(定长最小单元+变长数量+一次性长度声明)。补刀:排版求解器遍历UI树≠树被计算用——求解器是装配器族(读蓝图/声明产位置和绘制清单),合成器(读帧产帧)仍不碰树。

- **MC地图存储/内存/渲染取证(2026-10-14 三问取证)**:①**磁盘小三件套**:区块16×16×全高切成16³区段(1.18起24段),每段存**调色板+位打包索引**(位宽=⌈log₂调色板大小⌉下限4位,单值调色板连数据数组都不存;>256种才退化15位全局调色板)→普通区段2KiB vs 天真8KiB;**稀疏即缺席**(全空气区段不存/未探索区块不存在);NBT+zlib压缩(新版可选LZ4)。32×32区块打一个.mca区域文件,4KiB扇区对齐是唯一浪费。常见误解澄清:**MC不是存"种子+增量"——区块生成即全量物化落盘**,小靠调色板+缺席+压缩不靠种子。②**内存=税不付清解码常数化**:加载后不展开成每块int,保持调色板+位打包原样(读一块=掩码+移位+查表常数时间),**区段位宽=该区段创建时一次性声明,数组=4096×b位定长——又一个"声明可变地址定长"实证**;写入超阈值才重声明位宽重打包;空气区段=null快路径;光照另存(方块光+天空光各4位/块);ticket系统管加载卸载,1.18起模拟距离/渲染距离分离。③**渲染七连剔**:烘焙期隐藏面消除(只产可见面,实心山内部=零几何,区段只剩表面壳);**可视图遮挡剔除**(烘焙时算区段内空气连通性,运行时从相机区段BFS只沿连通扩散,墙后洞穴不提交——最极致一招);视锥剔除(per-区段AABB);近→远不透明吃early-z/半透明远→近;光照AO烘焙进顶点色;**脏了才重烘**(改动标记区段脏+每帧重建预算,不脏复用千百帧=以查代算);距离硬截断+实体距离剔除+雾遮断线。诚实:vanilla无LOD(远处靠截断,LOD是mod用八叉树),无贪心网格合并(OptiFine/mod的活)。**映射宪法**:磁盘=缺席不物化+调色板稀疏声明+压缩税;内存=声明可变地址定长;渲染=烘焙帧+脏标记(以查代算/变了就渲)。
