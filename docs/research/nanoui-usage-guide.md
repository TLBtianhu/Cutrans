# nanoui 使用说明（OTTO 侧的经验与精化清单）

> 写给 Cutrans：你们准备用 nanoui 做图形界面。这份是我们（OTTO）**在生产里用过之后的判断**，
> 不是官方介绍。包含：它是什么、哪部分好用、哪部分要避、我们正在精化的地方、以及接入建议。
> 日期：2026-11-03。上游当前 release **v0.11.0**，我们的 fork 分支 `otto-091`（已合并到 0.10.0）。

## 一、它是什么

**纯 Zig 的原生 UI 库**：自己管窗口、文字（DirectWrite）、图像、输入与渲染，
**零 C 依赖、不用 `@cImport`**，Windows 下直接走 Win32 / DWrite / D3D11 / GDI。

**适合**：想要"一个小体积、无运行时的原生桌面应用"。
**不适合**：想要浏览器式的富文本/复杂排版/现成控件库（它不是那个）。

## 二、我们觉得好的部分（已在生产验证）

| 部分 | 我们的评价 |
| --- | --- |
| **窗口与输入** | 稳定，`non_activating`、无边框、置顶这些都能用；上游响应很快（我们的 #35 已实现） |
| **IME / CJK** | 我们提的 **#34（CJK 字体）与 #36（Windows IME）已进上游**，中文输入可用 |
| **渲染（GDI）** | 文字清晰（RGB ClearType），是老机器/远程桌面的兜底路径 |
| **模型简单** | 一个 view + 一个 atlas + 事件，没有隐式全局状态，便于做内存预算 |

## 三、要避或要小心的部分

| 部分 | 问题 | 我们的处理 |
| --- | --- | --- |
| **D3D 文字（0.11 及之前）** | 只上传 R8 灰度图集、单 alpha 画字形，**文字发虚** | 我们已修成 **RGB 子像素**，并提了 **PR #71** |
| **`--nanoui-snapshot`** | **固定走 CPU 光栅**，不能用来判断 D3D 画质 | 判断 D3D 必须用真实窗口 readback |
| **WebView2 页面（0.10+）** | 默认要 **WebView2 SDK**，不装就构建失败 | 不用就 `.webview2 = "none"` 关掉 |
| **字体加载** | 没有索引缓存，冷启动要扫字体目录；字体文件会整份复制 | 我们做了**字体索引缓存 + mmap**，还没上游化 |
| **默认 target** | `standardTargetOptions(.{})` 默认 native，会按构建机 CPU 编译 | **必须钉基线**（我们钉 `x86_64_v2`），否则老 CPU 直接非法指令 |
| **图集/缓存** | 图像图集、缩略图、PCM 都要自己管预算，不然内存会悄悄涨 | 我们把 L2/预览/PCM 都做了**硬预算** |

## 四、我们的 fork 里有什么（上游还没有的）

**已经在用、但还没上游化**：

- **字体索引缓存**（按字体目录 mtime+size 做键，热启动不扫盘）；
- **mmap 字体**（只读映射，DirectWrite 借用字节，不再每种字体复制一份）；
- **原始 BGRA 像素绘制**（我们提过，但上游 images.zig 也已有 BGRA atlas，注意别重复）；
- **帧日志 / trace、frame_timing**（性能诊断，默认关）。

**已提回上游的**：

```

#36  Windows IME（已合并）
#70  Windows 文件拖放（WM_DROPFILES → ui.Drop，待审）

```

## 五、我们正在精化的部分（尚未定稿，别照搬）

### 1. 文字清晰度
D3D 的 RGB 子像素已经修好（0.56 / PR #71），但**用户仍觉得不够清**。
现在在查的是**字体本身、gamma/contrast、hinting**，并用**原生 Windows ClearType 做对照**。
**结论**：D3D 灰度问题已解决，剩下的是"字到底该多锐"的调校，**还没定稿**。

### 2. 响应式布局（窗口拉伸重排）
我们做了一套**小的布局求解器**（fixed / fraction / minmax 轨道 + 容器断点），
原则是**重排而不是等比缩放**：

```
断点落在**容器宽度**上，不是窗口宽度
让位顺序固定：先辅助列（采样率 → 格式/大小），**文件名从不先被压缩**
字体大小、行高、点击目标不随窗口变
只在容器尺寸真的变化时重算
```

**正在改的**：断点跳变太硬，改成**连续分配**（名称列连续吃剩余，辅助列快不够才让位），
并加**恢复默认窗口大小**的动作。
**结论**：方案可用但**还不够顺手**，等调顺了再考虑提给上游。

## 六、给 Cutrans 的接入建议

### 版本与构建
```
1. 用 **vendored 固定版本**，不要 floating 跟上游 main（上游更新很快，一周能出两个 release）
2. **默认 target 钉在 x86_64_v2**（SSE4.2），开发机要更快用显式 -Dcpu=native
3. 不用 WebView2 就 **`.webview2 = "none"`**，否则要装 SDK
```

### 性能与内存
```
- 缩略图/图集/PCM 都设**硬预算**，且按**峰值**判断，不看回落后的当前值
- 首帧这种指标被 Windows 侧成本主导（建窗口约 58 ms），**别拿它衡量 SIMD 优化的收益**
- 字体：先用系统字体索引，冷启动慢再考虑缓存（我们的方案可参考）
```

### 测试习惯（我们踩过的）
```
- 判断渲染质量：**真实窗口 readback**，不要用 snapshot 代替
- 任何"优化"都要能**反向失败**（关掉开关必须变差），否则分不清优化和机器安静
- 测性能前**确认二进制是 release**（debug 会差一个数量级）
```

## 七、一句话总结

**nanoui 是"小而可控"的原生 UI 库，值得用；但要自己管预算、钉基线、并知道它的 D3D 文字在 0.11 之前是灰度的。**
我们和上游的关系是**互相反哺**：他们收我们的 IME/CJK，我们跟他们的窗口与输入模型。
**正在精化的只有两件事：文字的"该多锐"，和布局的"该怎么重排才顺手"**——这两件定稿后会考虑上游化。
