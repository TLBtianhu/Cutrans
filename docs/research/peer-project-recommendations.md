# 跨项目设计复核与下一步建议

> 用途：按项目拆段，分别交给对应项目的 Agent。
>
> 涉及：`C:\MediaForge`、`C:\deepseek直播`、`C:\src\nanoui`、`C:\src\otto-zig-lite`、`C:\src\zig-audio`、`C:\src\OTTO-sample-manager`，并以 Cutrans 作为对照。
>
> 复核边界：本文依据项目文档、记忆和关键实现的静态阅读形成，没有运行这些外部项目，也没有把文档中的测试数字当作本次实测。各项建议落地前，接收方应先读取本项目的 `AGENTS.md`、记忆和当前工作区状态；已经完成的项目直接划掉，不要重复建设。

## 一、共同的设计纪律

这些项目表面上分别做 UI、素材、媒体处理、解码和直播，底层反复出现的是同一组问题。

1. **一个事实只能有一个写者。** 索引、视图和缓存都可以是投影，但不能各自反写同一份真源。多写者之间做“写前合并”只能减少损失，不能替代单写者。
2. **声明、就绪、执行结果是三件事。** 注册了一种格式不等于本机可运行，本机可运行不等于这次输入有效，进程退出码为零也不等于所有产物成功。
3. **接受命令不等于执行成功。** `accepted` 只代表入队；最终结果必须来自稳定任务 id 对应的终态事件。
4. **永久身份与运行实例分开。** 用户配置、权限和资产跟随稳定 id；版本、进程、模型槽和渲染实例可以替换、预热和回滚。
5. **显示端只接收投影。** UI、Presenter、Outlet 不拥有业务真源。跨信任边界传声明式描述，不传任意可执行渲染逻辑。
6. **不支持与执行失败不能混淆。** `unsupported/no_handler` 可以谢绝并询问下一个 provider；认领后的 `corrupt/failed/missing` 应保留最具体的失败，不能被后续兜底粉饰。
7. **数据流要计算物化成本。** 多次解码、多次编码、逐帧落盘、整文件复制、重复模型加载都是真实成本，不能只看函数调用是否优雅。
8. **开发、便携、安装是三种运行形态。** 编译产物不写用户状态；便携版数据随程序走；安装版数据在用户目录；三者路径分离并可同机共存。
9. **测试必须能故意失败。** 跳过、空数组、没有样本、没有 GPU、没有 ffmpeg 都不能静默变成“通过”。开发能力测试与全新用户环境验收分开。
10. **线程、VM、Worker 不自动等于安全沙箱。** 不可信代码需要操作系统级进程、权限、文件系统和网络边界；凭证不进入执行域。

## 二、MediaForge

### 已经值得保留的基础

- Capability、Model、Binding、Adapter 分离，声明表与注册实现能够对账。
- 多步视频工作流已经把步骤合并到逐帧执行中，通过 FFmpeg rawvideo 管道共享一次解码和一次编码。
- OperationKernel 已有进度节流、终态、取消、重启后的 `interrupted` 和历史保留策略。
- 模型根、工具定位、下载哈希、下载看门狗和运行时诊断已经走过真实事故，不应再另起一套路径或下载逻辑。

### P0：先完成干净用户环境验收，再增加模型和功能

项目记忆末尾已经明确：安装包与便携包已经产出，但还没有完整“装完能跑”的实机验证；运行时准备脚本也仍有探针问题。这是当前最优先的短板。

建议：

- 先修复标准运行时准备/诊断入口中的 `av` 探针，不能绕过标准脚本另造一个能成功的旁路。
- 分别用全新的程序目录、数据目录和模型目录验证开发版、便携版、安装版；三者不得通过 junction、环境变量或缓存暗中共享。
- 完整走过：启动 → 诊断 → 定位 FFmpeg → 下载一个小模型 → 执行一个最小任务 → 取消一个任务 → 重启查看任务历史。
- CUDA 与 CPU 分开报告；没有 GPU 时验证明确的不可用状态，不把未执行记作通过。
- 更新源和镜像在暂存环境验证下载、校验、覆盖应用层、保留数据与回滚；不要为了测试直接覆盖正在使用的真实环境。

**验收：** 一个从未接触过仓库的新环境，只按发布说明即可完成最小任务；测试结束后说明程序、数据、模型、缓存分别落在何处。

### P0：把任务索引真正改成单写者

当前 `python/core/operation_kernel.py` 会通过目录差集吸收 Rust 写入的作业，项目记忆也明确承认 `index.json` 仍有两个写者。这是兼容措施，不是最终形态。

建议：

- 由一个内核独占索引和任务状态转换；Rust/UI/MCP 只提交命令或追加事实，不直接重写总索引。
- 为每次状态变化提供稳定 `jobId + serial`，重复事件幂等，旧事件不能覆盖新状态。
- 统一取消入口；跨进程文件只保留为传输细节，不能形成两套语义。
- 保留“重启后遗留 running → interrupted”和“终态不可复活”的规则。

**验收：** 并发覆盖 UI 与 Agent 同时启动、查询、取消同一任务；强制杀死 worker 和内核后重启；旧事件、重复终态和外部慢写入都不能造成任务丢失或状态倒退。

### P1：用 ProcessingPlan 收束音频、媒体和命名工作流

这应与现有路线合并，不另建一套“统一架构”。

- 单模型任务、媒体步骤、音频图节点都只生成同一种计划；工作流保存计划，不保存页面私有状态。
- 组合能力只存在于工作流，不把“超分+去水印”重新硬编码成第三种业务模式。
- 页面只编辑计划和绑定；队列、结果、取消、诊断仍归全局内核。
- 命名工作流要记录 schema 版本、能力 id、模型绑定和参数；模型改名不能靠字符串嗅探修复旧计划。

**验收：** 同一计划在 GUI 与 MCP 中得到相同规范结构和执行结果；音频图与媒体工作流不再各自解释 capability。

### P1：让下载和取消真正拥有执行过程

现有看门狗能发现“不再增长”，但守护线程报告超时并不自动等于底层阻塞下载已经停止。

- 核对每个超时、取消和失败路径：谁拥有线程/进程，谁关闭响应，谁还能继续写 `.part`。
- 每次尝试使用独立临时文件，完成后校验大小与哈希，再原子转正；旧尝试不得覆盖新尝试。
- 同一模型同一版本只允许一个装配写者，其他请求等待同一结果。
- 超时应产生可恢复错误和明确状态，不留下永远运行的后台线程或半份可用模型。

### P1：流式视频继续补时间语义与故障语义

现有“一次解码、一次编码”方向正确，下一轮不应退回到逐步中间视频。

- 明确 VFR、时间戳、音画同步、首尾帧、异常短帧和输出尺寸变化的规则。
- 不用静默的 fps 猜测冒充源制式；无法确认时要给出具名降级。
- 核对取消是否能及时打断管道读写，以及编码器、解码器退出后的 stderr 和退出码传播。
- 减少整输入复制等非必要物化，但必须先保证路径兼容与诊断能力不退化。

**验收：** 至少覆盖带音轨短视频、VFR 样本、损坏输入、中途取消、编码器失败；检查帧数/时长/音轨，而不只检查输出文件存在。

### 暂不建议

- 在干净安装和任务单写者完成前继续扩模型数量。
- 为每个页面新增本地队列、私有下载器或私有模型路径。
- 为追求“自动恢复”而让 CUDA 失败静默落到 CPU 长跑；fallback 必须可见、可取消。

## 三、deepseek直播 / Fishbowl / Habitat

### 已经值得保留的基础

- Director、AI Client、Presenter、Outlet 分责明确，Presenter 与 Outlet 不持有业务真源。
- 客户端提交声明式 `SceneDescriptor`，而不是提交渲染代码。
- 技能身份挂在 id 上，版本实例是槽；命令闭集、能力检查和回滚已有可运行骨架。
- 已明确要求真正的不可信执行进入 OS 沙箱，而不是把 Worker 当作安全边界。

### P0：先修技能运行时的多租户与迟发事件

`runtime/skill-runtime.mjs` 的 `_collectGarbage(exceptKey)` 当前遍历并终止除新槽外的所有槽。若多个技能共存，激活或回滚一个技能可能清掉其他技能的活槽，应优先用测试确认并修正作用域。

建议：

- 垃圾回收、drain、history 和 rollback 都按技能 id 隔离。
- `call()` 超时后移除消息监听器，并处理迟发 result；不能让每次超时永久积累监听器。
- init 超时、worker exit、主动 drain、自动回滚必须能区分，主动回收不能记成崩溃。
- 回滚操作串行化，旧代回滚不能覆盖更新的激活代。

**验收：** A、B、C 三个技能同时存活；反复激活 A 不影响 B/C；A 超时与回滚期间 B 的调用继续成功；大量超时后监听器数量不增长。

### P0：给 PhaseMachine 加合法转换表和外部副作用协议

当前 `director/phase-machine.mjs` 的 `to()` 检查目标相位是否存在，但没有统一的合法边表；本地状态回滚也不能自动撤销已经发生的 world/presenter 副作用。

建议：

- 用显式转换表拒绝非法跳转，而不是只依赖各入口函数里的零散判断。
- 每次转换带 `transitionId`，外部动作幂等并可确认；失败时进入明确的补偿或对账流程。
- `quiesce` 超时后只有在取消得到确认时才能声称完成；否则应报告降级或失败。
- Presenter/World 的确认值要能从快照或事件日志重建，不能只存在调用栈里。

**验收：** 对每个适配器分别注入保存失败、scene 失败、drain 超时和取消失败；不得出现“日志显示失败，但世界已进入下一相位”的假一致。

### P0：收紧 Display Server 的本机控制面

`display/server.mjs` 当前有通配 CORS、未认证 POST 和 `/shutdown`，请求体也缺少明显的大小与结构限制。绑定 loopback 并不能阻止本机其他进程或网页向本机端口发请求。

建议：

- 控制面与只读状态面分离；默认关闭远程访问和任意来源 CORS。
- 每个客户端使用短期、可撤销的 capability token；token 不写入场景、日志或快照。
- 限制请求体大小、快照大小、客户端 id 字符集和 surface 数量；未知字段与非法事件明确拒绝。
- `SceneDescriptor` 增加 schema 版本、单调 revision、过期时间；旧 revision 不覆盖新场景。
- shutdown、remove 等管理动作不能与普通场景提交拥有相同权限。

### P1：把 Outlet 的进程身份交给真正的监督者

`control/outlet-host.mjs` 通过 pidfile 和 `kill(pid, 0)` 判断存活，存在 stale pid 与 PID 复用后误停其他进程的风险。

- 优先由 systemd、Job Object 或长期监督进程持有子进程身份，而不是只相信 PID 数字。
- 若必须保留 pidfile，增加启动令牌/进程实例校验和原子状态文件。
- 启停操作幂等，停止必须等待真实退出并处理超时。
- 推流配置权限检查继续保留；任何日志和诊断都不能输出 stream key。

### P1：把“播放头诚实”变成可观察协议

- 每帧带 `sourceId / sequence / capturedAt / presentationAt`。
- Presenter 与 Outlet 分别报告帧龄；陈旧阈值到达后切待机或黑场，不将定格旧帧当成实时。
- AI Client 崩溃时 Outlet 继续编码待机卡；Presenter 重启不能要求 Director 重建业务真源。
- 本地录制与推流分别报告失败，不能让一个出口的成功掩盖另一个出口失败。

### 暂不建议

- 为了“无头显示器”继续扩大 HTTP 面；信任与生命周期没收紧前，不暴露到非 loopback。
- 把宿主 shell、任意文件系统、computer-use 直接交给 AgentLoop。
- 在 Worker 内执行第三方代码后就宣称已沙箱化。
- 同时扩展更多相位、客户端和 Outlet；先让现有失败矩阵可信。

## 四、nanoui

### 已经值得保留的基础

- 轻量立即模式 UI、稳定控件 id、虚拟列表和上一帧布局命中的方向正确。
- 无窗口测试、CPU/GPU 渲染对照、性能基准和空闲零轮询已经成为工程纪律。
- 文档明确承认平台能力边界，没有用“跨平台”掩盖尚未支持的功能。

### P0：把帧一致性做成跨后端的不变量

- 输入命中必须针对用户实际看到的上一帧；异步数据到达、窗口 resize、DPI 改变后先重建，再绘制，再接受新命中。
- 对焦点、hover、pressed、scroll anchor 和文本选区分别定义状态归属，不能全部跟随列表行号。
- 用脚本覆盖“点击与数据更新同帧”“滚动与过滤同帧”“resize 与异步图片到达同帧”。

**验收：** 同一交互脚本在支持的后端得到相同语义结果；像素允许平台差异，但焦点、选择和命令序列必须一致。

### P0：可访问性跟随语义树，而不是另做视觉补丁

README 已明确可访问性只覆盖部分平台。建议按项目实际支持的平台逐步补齐，不为追求表格全绿做假接口。

- 控件角色、名称、值、禁用、焦点和公告来自同一份语义树。
- 虚拟列表只物化可见行，但对辅助技术提供正确的总数、位置与滚动能力。
- 键盘导航、IME composition、高对比度和字体缩放分别验收；不要把 IME 当成普通键盘字符流。

### P1：性能数据增加平台与生命周期口径

现有 M3 数据有价值，但不能自动代表 Windows、低端 GPU 或真实应用。

- 分开记录冷启动、暖启动、隐藏窗口、可见窗口、持续动画和完全空闲。
- 同时报告 CPU 帧时、GPU 帧时、驻留内存、线程数、图集增长和缓存上限。
- 每项基准标明 OS、后端、构建模式、素材规模和是否有窗口；回归阈值只用于稳定环境。
- 对“零轮询”做行为测试：无输入、无动画、无后台就绪事件时，不应被隐藏计时器持续唤醒。

### P1：稳定 id 要穿透过滤与复用

- 过滤、排序、分页、虚拟列表复用时，选择应跟随稳定 item id；无法保留时明确清除，不悄悄改指另一个项目。
- 控件复用后不得继承旧行的 pressed、文本 composition 或拖动状态。
- 为 id 冲突提供开发期诊断；不要默默覆盖状态表。

### 暂不建议

- 先增加更多装饰性控件或玻璃效果，再补焦点、IME、可访问性和异步帧一致性。
- 为每种平台缺陷引入应用侧特判；应先修框架契约。
- 把单一机器的基准数字写成普遍性能承诺。

## 五、OTTO Lite

### 已经值得保留的基础

- Preview Provider/Outcome 把视图与格式解耦，四态谢绝规则非常清晰。
- 第三方 Shell 缩略图有独立 helper、超时和有界队列；元数据与解码能力分离。
- OTTOLIB 按 magic 识别、原子写入、损坏错误具名；无头导入、预览、过滤、分发检查较完整。
- 开发、便携、安装和更新检查已有较多真实进程验收，不需要重起一套发布框架。

### P0：统一 helper 不可用时的契约

当前文档与实现存在需要作者决定的差异：应用 README 说 helper 缺失应是启动错误、不静默退回；`preview.zig` 与 `providers/thumb.zig` 则描述并实现了 `HelperUnavailable` 时退回进程内取图。`Timeout` 不退回这一点是一致的。

建议：

- 选择一种生产语义，并让 README、代码注释、启动诊断和实现一致。
- 更倾向于“默认隔离，helper 缺失给出具名失败；只有显式对照开关允许进程内”，避免隔离配置悄悄失效。
- 若作者选择保留自动退回，也必须在结果与诊断中显示实际执行域，不能声称本次走了隔离。
- 继续保持：handler 超时或崩溃后绝不把它重新请回主进程重试。

**验收：** 在临时分发副本中模拟 helper 缺失、启动失败、超时和崩溃；结果、日志和实际进程路径与选定契约一致，不影响开发目录。

### P1：合并重复取图，但保留不同预算

`providers/thumb.zig` 已记录 64px 行内图和 256px 预览可能重复取图。

- 用文件身份、大小、mtime、请求尺寸、像素格式、provider 版本组成缓存键。
- 可由一次较大取图派生小图，但不能为了小图标解码整段媒体。
- 缩略图与完整预览仍分别计量预算；缓存失败要有原因和失效策略，不永久缓存一次暂时失败。
- helper 重启或 provider 更新后，缓存版本必须能区分旧结果。

### P1：新增 provider 时保持失败语义不被稀释

- `supports` 只做廉价声明，真正的内容识别仍在 `open`。
- `failed/file_missing` 终止查找；不能被后面的通用 Shell provider 变成一张看似成功的图标。
- 元数据可解析不等于内容可播放；部分可解的前缀与下一次读取错误要保持明确。
- provider matrix 若缺少关键样本或 provider，应在要求覆盖的 CI 中失败，不能全部跳过后显绿。

### P1：更新验收走到真实安装与数据保留

现有更新检查、签名、下载和“不执行安装”的测试很好，下一步是用户形态闭环。

- 在隔离的全新安装目录与数据目录执行真实更新，不碰日常数据。
- 验证覆盖应用层后库、设置、生成资产保留；旧版本仅保留必要回滚副本。
- 便携版不被安装版更新器替换；开发产物不写更新状态。

### 暂不建议

- 为增加格式数量而绕过 Outcome 四态。
- 为省一次取图引入无上限缓存或永久负缓存。
- 把 Lite 与原版强行合并成一次大重写；先复用语料、契约和核心模块。

## 六、zig-audio

### 已经值得保留的基础

- 解码器边界窄、无全局状态、调用方提供缓冲，`read()` 不隐藏分配。
- 错误分类明确，不用静音替代错误；FLAC 保留可解前缀、下一次读取再报错。
- 小样本、FFmpeg 逐样本对照、官方向量哈希和变异 fuzz 已形成可信验证体系。

### P0：让集成测试的跳过变得可见且不可误用

README 说明本机 FFmpeg 路径写死，缺失时集成测试会 skip。这对便利开发合理，但不适合作为唯一发布门。

建议：

- FFmpeg 通过显式环境变量、配置参数或可审计发现机制传入，不再依赖某台开发机的固定路径。
- 测试分为：纯库测试、固定小样本对照、外部向量、实时 FFmpeg 对照、长 fuzz。
- 至少一个发布 CI 环境保证 FFmpeg 和必需样本存在；该环境发生意外 skip 必须失败。
- 输出实际执行的样本数、比对样本数和跳过原因，避免“收集很多测试但关键路径没跑”。

### P0：把 ShortBuffer 与前缀语义做成全格式矩阵

- 每种解码器都用 1 字节、极小缓冲、非帧对齐缓冲和随机缓冲大小读取。
- 验证短缓冲不破坏内部状态，不重复或丢失样本，不触发隐藏大分配。
- 对可解前缀后遇错的格式，明确首次返回前缀、后续返回错误的统一规则；不能某些格式静默补零。
- 将 `NotAudio/Unsupported/Truncated/Corrupt/Io` 的映射做成跨格式契约测试。

### P1：把 fuzz 成果沉淀为永久回归语料

- 每次崩溃或越界保存最小化样本、结构说明和预期错误，不只依赖随机种子。
- 对 Ogg lace/packet 边界、Opus TOC、FLAC bit reader、AIFF 大端长度和 ADPCM 块边界做结构化变异。
- 除“不 panic”外，继续断言内存上限、输入长度上限、错误具名和 deinit 平衡。
- fuzz 发现的不支持编码可以明确拒绝，不要为了消除错误而接受无法正确解释的流。

### P1：性能与资源预算按格式报告

- 验证 `read()` 的分配次数、峰值内存和每样本成本，区分 open 与 steady-state。
- 并发打开多个 decoder，证明没有全局缓存串扰。
- 基准使用 Release 构建并记录 CPU、输入、缓冲和样本格式；不把 CI 噪声变成不稳定的硬阈值。

### 暂不建议

- 为格式数量继续扩编解码器，而缺少官方向量、故障语料和参考对照。
- 把容器、编码、声道混音、播放设备重新揉进一个“大音频 API”。
- 为通过 fuzz 把损坏输入转成静音。

## 七、OTTO Sample Manager（Tauri 主线）

### 已经值得保留的基础

- 产品优先级围绕真实制作流程：导入、试听、整理、拖出、复用、活字印刷，而不是素材库外观。
- 自动副本、生成资产长期保留、SQLite WAL、窄 DesktopBridge 都是正确方向。
- 安装版、便携标记、签名更新和数据目录已有明确入口，应先增强这些路径，不另造平行机制。

### P0：重新核对“第一次拖出使用原件”的保护语义

README 当前写明第一次拖出使用原文件、第二次开始使用副本，但同时又把防止 Melodyne 污染原素材列为主要目标。若宿主第一次就修改文件，计数式保护已经来不及。

建议：

- 对已知会修改素材的宿主，默认每次拖出都使用受控副本；明确的高级选项才允许直接使用原件。
- 若保留计数策略，必须在 UI 和文档中明确第一次也有原件风险，不能宣称完全保护。
- 副本身份跟随稳定 asset id 与用途，不依赖当前列表顺序；重启、多选和并发拖出不能重复计数或互相覆盖。
- 副本创建使用独立临时文件和原子完成，取消或崩溃不得留下可被误认为完整的副本。

**验收：** 用真实会修改文件的宿主走第一次、第二次、并发和重启后拖出；原件哈希始终符合所选保护策略。

### P0：把四类数据从目录名称升级为生命周期契约

至少区分：

1. 用户原始素材；
2. 为外部软件生成的使用副本；
3. 活字印刷等长期生成资产；
4. 波形、索引等可再生成缓存。

建议：

- 清理缓存绝不能碰 1 和 3；清理普通副本前也要确认没有外部项目正在引用。
- 长期生成资产应有可查看、导出、打开位置和显式删除入口，不能只因为放在 `Copy` 下就变成难以管理的隐藏文件。
- 资产清单记录来源、生成参数、创建时间、哈希和保留类别；路径改变不改变身份。

### P1：活字印刷先做确定性计划与 dry-run

当前“重复候选取第一个、缺失继续”适合提高生成率，但还需要可解释性。

- 候选按稳定规则排序并记录选择原因；“第一个”不能依赖文件系统或数据库返回顺序。
- 生成前报告匹配、缺失、歧义、多音字、声调丢弃和预计复制量，让用户确认后再执行。
- 输出 manifest 保存歌词原文、归一化规则、源 asset id、源哈希、顺序和缺失项。
- 同一计划重复执行应幂等；取消和失败不能留下一个看似完整的分组。
- 生成结果是新资产，不反向修改源分组和原文件。

### P1：后台导入与生成共用任务账本

- 导入、索引、活字印刷和副本生成使用统一任务状态、进度、取消与结果，不在各弹窗维护私有生命周期。
- 重启后未完成任务标为 interrupted 或可明确恢复，不永久显示 running。
- DesktopBridge 保持闭集命令和参数校验；前端不能借任务参数重新获得任意路径或 SQL 能力。

### P1：发布验收覆盖数据，而不只覆盖启动

- 开发、便携、安装三种形态使用不同程序与数据路径，可同机共存。
- 升级后保留原素材索引、生成资产、设置与凭证；缓存可重建。
- 安装版更新只覆盖应用层；便携版继续只打开发布页或由明确的便携更新流程处理。
- 真实 DAW 拖放与自动更新需要人工验收，不用无头模拟冒充已经通过。

### 暂不建议

- 立即用 OTTO Lite 重写整个产品；先共享音频测试语料、格式契约和可独立复用的核心。
- 为提高活字印刷“成功率”而静默选择不确定候选。
- 用统一“清空 Copy”解决磁盘问题，生成资产与普通副本必须不同治理。

## 八、Cutrans 自身也要保持的自省

Cutrans 在这次对照中提供了几条有用经验，但不是完成度范本，其他项目不应照搬它的未完成任务。

可输出的经验：

- `.cut` 声明树、指纹与物化分离；声明上存在不等于像素已经就绪。
- Command 帧边界提交，`accepted` 与最终结果分开；Task 终态不可改写。
- Surface 的 configuration serial 与呈现确认，让异步配置不再只依赖“窗口大概已经调整好”。
- 开发、便携、安装路径隔离，测试从真实用户入口走完整链路。

仍需自己补齐：

- History 尚未持久化，Stream 仍是静态文档流，真实视频播放、音频和完整插件隔离尚不存在。
- 固定数量的 Surface、Task、节点与命令参数缓冲需要明确的容量错误和后续增长策略。
- `over` 仍有兼容求值路径，不能把 DAG 骨架说成完整通用图像内核。
- 真实 GUI 的视觉、手感、IME 与长期交互仍需实际验收，无头测试通过不代表这些已经完成。

因此，各项目应借鉴 Cutrans 的约束和验证方式，而不是等待它先提供一套“统一总框架”。

## 九、可以共享语义，但暂时不要共享大依赖

各项目可以逐渐对齐以下概念，便于以后交换语料和诊断，不建议现在建立 monorepo 或公共运行时大包。

### 1. 失败语义

```text
unsupported / no_handler / not_ready / missing
corrupt / failed / cancelled / interrupted
```

每个项目可以保留自己的错误枚举，但应回答相同问题：是否认领、是否可重试、是否可换 provider、是否是终态。

### 2. 任务语义

```text
jobId + source + subjectId + revision + serial
queued / running / succeeded / failed / cancelled / interrupted
progress + outcome + diagnostic
```

`source` 区分 GUI、CLI、Agent，不因此建立第二套任务系统；`serial` 防止旧事件覆盖新状态。

### 3. 资产与测试素材

```text
origin + license + sha256 + byteLength + acquisitionCommand
```

外部测试素材记录来源和许可证，固定小样本入库，大向量按需下载并校验；下载失败不能静默跳过发布验收。

### 4. 预览与运行形态

- 预览的 provider、降级原因和实际执行域可诊断。
- 开发、便携、安装的诊断输出包含真实程序根、数据根、缓存根，但不输出凭证。
- “已声明支持”“本机可用”“本次成功”分别展示。

## 十、给各 Agent 的首个建议切片

| 项目 | 首个建议切片 | 完成判据 |
|---|---|---|
| MediaForge | 干净安装/便携验收 + 任务索引单写者设计 | 新环境最小任务真实成功；并发、取消和重启不丢任务、不倒退 |
| deepseek直播 | SkillRuntime 多租户与 PhaseMachine 失败矩阵 | 多技能互不误杀；所有适配器失败都有明确、可对账的相位结果 |
| nanoui | 异步更新/过滤/resize 同帧交互夹具 | 各后端语义一致，无错位命中、焦点串行或复用污染 |
| OTTO Lite | 统一 helper 缺失契约并做真实故障验收 | 文档、日志、结果和实际执行域一致，超时不回主进程 |
| zig-audio | 不可误跳的 FFmpeg 集成门 + 全格式短缓冲矩阵 | 关键 skip 会失败；缓冲切分不改变样本与前缀错误语义 |
| OTTO Sample Manager | 原件保护 + 活字印刷 dry-run/manifest | 原件不被宿主污染；候选、缺失、生成来源与结果可解释、可复现 |
